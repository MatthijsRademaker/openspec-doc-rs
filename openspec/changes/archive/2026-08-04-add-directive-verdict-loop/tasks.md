Deliberately not auto-created by the hook: `promote::check` skips a session with no note, and creating one for every session would make every open session promote on the first new change, with concurrent sessions renaming their notes onto the same change path.

## 2. Verdict-to-directive translation

- [x] 2.1 Define fixed reason-text templates for keep-exploring, move-to-proposal, and comment-resolution verdicts, each naming relevant sidecar/artifact paths. Each template MUST be an attributed pointer — it states that it is review feedback from this project's openspec-doc dashboard and names a path in the repo to read — and MUST NOT be a bare imperative. A receiving agent can otherwise reject the directive as prompt injection even though the hook delivered it correctly; see design.md.
- [x] 2.1a Document the hook mechanism in this repo's `AGENTS.md`: that openspec-doc may inject review directives at turn boundaries, where directive/comment sidecars live, and that these originate from the user's own dashboard. This gives a receiving agent legitimate in-project context for the directive instead of leaving it unattributed.
- [x] 2.1b The comment-resolution template MUST instruct the agent to report back with `openspec-doc comment reply` and MUST NOT instruct it to resolve a comment. Resolution is the reviewer's acceptance of the work, not the agent's claim to have done it; an agent that closes its own threads defeats the review loop. `add-comment-thread-actions` adds the `addressed` status the agent sets instead, and revises this template to use it once that change lands.
- [x] 2.2 Implement lookup of an untranslated phase-verdict record for the session/change at hook-stop time
- [x] 2.3 Implement translation into the pending-directive file format from `add-agent-hook-bridge`
- [x] 2.4 Mark the verdict record consumed/translated so it is not translated again on a later invocation
- [x] 2.5 Add tests for each verdict kind: correct reason text produced, no embedded comment content present, verdict marked consumed
- [x] 2.6 Add a test over every template asserting it names at least one in-project path and identifies itself as dashboard review feedback, and that none instructs the agent to emit specific literal output
- [x] 2.7 Add a test asserting no template instructs the agent to resolve a comment

## 3. End-to-end proof

- [x] 3.1 Run a real Claude Code session in this repo with `openspec-doc hook stop --agent claude` wired as the Stop hook and the dashboard open
- [x] 3.2 Submit a "keep exploring" verdict with a note from the dashboard; confirm the next Stop event blocks the session and the agent visibly acts on the injected reason. Delivery is not the bar: an agent that receives the directive and then declines it, questions it, or flags it as untrusted input counts as a FAILURE of this task — revise the templates per 2.1 and re-run. This is the only check in the whole change that can catch injection-rejection. **PASSED**, session `a020f7e4`: verdict "Lets dig deeper into the lingering server" submitted 08:48:54, directive written and consumed 08:52:48. The agent read the named files and acted — added a `## The lingering server, dug into properly` section, grew the note from 14.4KB to 28.8KB, reversed one of its own earlier conclusions and flagged the reversal, and reported back with `openspec-doc comment reply` **without** resolving the thread. No hedging, no injection challenge, no request for permission. The attributed-pointer template is vindicated against the bare-imperative one that was refused during `add-agent-hook-bridge`.
- [x] 3.3 Submit a "move to proposal" verdict; confirm the agent creates a change directory and the next Stop event promotes the scratch note and runs validate. **PASSED**, session `a020f7e4`: verdict translated and consumed 16:12:56, the agent created `add-dashboard-lifecycle`, and the following Stop promoted the note to `.openspec-doc/scratch/add-dashboard-lifecycle.md` with its 28,781 bytes intact, left the `openspec-doc:moved-to` redirect at the vacated session path, relocated the comment sidecar, and validated the change clean. The relocated comment re-resolved as `fuzzy` rather than `exact` — correct, since the note grew after the comment was anchored, and the anchor reports the drift instead of hiding it.
- [x] 3.3a Guard the promotion heuristic against cross-session attribution before relying on it again. Found while setting up 3.3: promotion diffs the active-change list against the session's snapshot and attributes any single new directory to that session, no matter who created it. A change directory created from a *different* session (this one) put session `a020f7e4` one step from promoting its exploration into `add-prompt-time-directive-delivery` and dragging its comment sidecar along. The `>1 = ambiguous` guard catches two-at-once but not wrong-author. Worked around by hand-advancing the session's snapshot to absorb the foreign change; needs a real fix in its own change.
- [x] 3.4 Repeat 3.2 for pi.dev's equivalent hook configuration. **PASSED**, session `019fcddd`, from a single scripted `pi -p` run: the agent seeded a `foo bar` scratch note and a keep-exploring verdict ("Work out whether the bar is load-bearing") for its own session via `$PI_SESSION_ID`, and at `agent_end` the hook translated the verdict, marked it consumed once, and the extension re-injected the reason. The agent then answered *the reviewer's question rather than the prompt it was given* — it wrote a `## Load-bearing assessment` section into the note, distinguished fixture semantics from runtime load-bearing, and stated a confidence level. No injection challenge, over a transport with nothing in common with Claude Code's. The extension's docstring claimed this was impossible to reproduce from a scripted harness; both cited quirks turned out to be tied to `--session-id`/`--continue`, and the docstring is corrected.
- [x] 3.5 Record the outcome of this end-to-end proof; treat any failure here as blocking before considering the MVP done. **The MVP's premise holds.** Nothing here was blocked. The loop ran on real sessions across both agents and all three verdict kinds that apply to a session, and in every case the agent treated the directive as legitimate project feedback: it read the paths it was given, did the work, and reported back. The risk this change was written around — that a correctly delivered directive gets refused as prompt injection, as happened during `add-agent-hook-bridge` — did not materialise once. Attribution plus in-project paths is what made the difference; confidence that the design is sound is now **high** where it was moderate-and-unproven. Two findings came out of the proof rather than the tests, both recorded above: promotion misattributes a change directory created by another session (3.3a), and a directive only ever arrives at the *end* of a turn, so the reviewer's own poke runs blind — addressed by `add-prompt-time-directive-delivery`.
